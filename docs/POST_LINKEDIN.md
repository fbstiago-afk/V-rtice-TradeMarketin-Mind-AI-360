## 🇧🇷 Versão em português

O modelo preditivo deste projeto deu **AUC 0,50** — o mesmo que jogar uma moeda.

E essa é a parte que eu mais faço questão de mostrar no dashboard.

Construí o **Vértice TradeMind AI 360**, um cockpit de Trade Marketing com duas camadas separadas de propósito:

📊 **Trade Marketing Intelligence** — sell-out, ruptura, execução de PDV, campanhas e promotores, com filtros sincronizados, drill-through por PDV e tabelas com micrográficos.

🧪 **AI Intelligence Lab** — onde RAG, classificação especializada, Guardrails e MLOps não são *explicados*: eles são **executados, avaliados e registrados**, e o Power BI lê essa telemetria real.

O que considero diferente aqui:

🔹 **Relatório como código** — 7 páginas, 170 visuais, 113 medidas DAX, bookmarks, RLS e drill-through gerados por um script Python que escreve TMDL e PBIR. O relatório inteiro é reprodutível, sem montagem manual.

🔹 **Cards em SVG renderizados por DAX** — KPIs com sparkline, barras em célula, selos de status e uma barra de contexto que mostra os filtros realmente aplicados. Sem visual de marketplace.

🔹 **Chat RAG de verdade dentro do Power BI** — um visual personalizado em TypeScript chamando uma API local por HTTP. Pergunta digitada no relatório, resposta com as fontes citadas e latência medida. Com a API desligada, ele avisa que está offline — porque não é um chat simulado.

🔹 **Guardrails testados, não ilustrados** — 10 cenários de segurança (acesso cross-tenant, dados pessoais, prompt injection na pergunta e no documento recuperado, consulta arbitrária) rodando contra o backend a cada execução. 10/10 com o comportamento esperado.

🔹 **Segurança em duas camadas** — RLS dinâmico por USERPRINCIPALNAME() no modelo semântico, e as mesmas regras reaplicadas na API. RLS de Power BI não protege um serviço externo.

🔹 **Número vem do modelo, texto vem do RAG** — perguntas numéricas vão para ferramentas tipadas com validação de parâmetros. RAG não substitui cálculo de indicador.

E a parte desconfortável: testei dois modelos de risco de ruptura, incluindo Gradient Boosting com defasagens de vendas. Ambos ficaram no acaso, porque a ruptura da base fictícia é aleatória. O catálogo de modelos marca os dois como **Rejeitado** e nenhuma previsão é publicada.

Dashboard que inventa previsão para parecer inteligente é fácil. Dashboard que mostra o experimento que falhou é o que eu levaria para uma reunião de diretoria.

## 🇬🇧 English version

The predictive model in this project scored **AUC 0.50** — the same as flipping a coin.

That's the part I most wanted to show *inside* the dashboard.

I built **Vértice TradeMind AI 360**, a Trade Marketing cockpit with two deliberately separate layers:

📊 **Trade Marketing Intelligence** — sell-out, out-of-stock, in-store execution, campaigns and field reps, with synced filters, store-level drill-through and tables with inline micro-charts.

🧪 **AI Intelligence Lab** — where RAG, specialized classification, Guardrails and MLOps aren't *explained*: they are **executed, evaluated and logged**, and Power BI reads that real telemetry.

What makes it different:

🔹 **Report as code** — 7 pages, 170 visuals, 113 DAX measures, bookmarks, RLS and drill-through generated by a Python script that writes TMDL and PBIR directly. The whole report is reproducible, with no manual assembly.

🔹 **SVG cards rendered by DAX** — KPIs with sparklines, in-cell bars, status chips and a context bar showing the filters actually applied. No marketplace visual.

🔹 **A real RAG chat inside Power BI** — a custom TypeScript visual calling a local API over HTTP. Question typed in the report, answer with cited sources and measured latency. With the API down it says it's offline — because it isn't a simulated chat.

🔹 **Guardrails tested, not illustrated** — 10 security scenarios (cross-tenant access, personal data, prompt injection in both the question and the retrieved document, arbitrary queries) run against the backend on every execution. 10/10 behaved as expected.

🔹 **Security in two layers** — dynamic RLS by USERPRINCIPALNAME() in the semantic model, and the same rules re-applied in the API. Power BI RLS does not protect an external service.

🔹 **Numbers come from the model, text comes from RAG** — numeric questions go to typed tools with parameter validation. RAG does not replace metric calculation.

And the uncomfortable part: I tested two out-of-stock risk models, including Gradient Boosting with lagged sales features. Both landed at chance level, because out-of-stock in the synthetic database is random. The model catalog marks both as **Rejected** and no forecast is published.

A dashboard that invents a forecast to look smart is easy. A dashboard that shows the experiment that failed is the one I'd take into a board meeting.

## Complemento — nota técnica sobre a demonstração

Para usar como primeiro comentário do post, ou como fechamento dele.

### 🇧🇷 Português

📌 **Por que a demonstração é em vídeo**

O chat RAG do relatório conversa com uma API que roda **localmente**, em Python. É ela que recupera os trechos, cita as fontes e aplica os guardrails no backend — a mesma camada que bloqueia pedido de dados pessoais e tentativa de prompt injection.

Num link público do Power BI o visual não alcança essa API: ele mostra *"Não foi possível acessar a API em 127.0.0.1. Nenhuma resposta foi gerada"* — exatamente o comportamento que programei para esse caso.

Preferi manter o visual dizendo a verdade a simular uma resposta bonita. Por isso o vídeo de 58 segundos: nele a pergunta é digitada dentro do relatório, a resposta volta com as fontes citadas e a latência medida, e o guardrail bloqueia um pedido de CPF ao vivo.

Publicar com o chat funcionando exigiria expor a API em HTTPS, com domínio próprio declarado nos privilégios do visual. É o próximo passo do projeto — não um atalho para a demonstração.

### 🇬🇧 English

📌 **Why the demo is a video**

The report's RAG chat talks to an API that runs **locally**, in Python. It retrieves the passages, cites the sources and applies the guardrails in the backend — the same layer that blocks personal-data requests and prompt-injection attempts.

On a public Power BI link the visual can't reach that API: it shows *"Could not reach the API at 127.0.0.1. No answer was generated"* — exactly the behaviour I programmed for that case.

I'd rather have the visual tell the truth than fake a polished answer. Hence the 58-second video: the question is typed inside the report, the answer comes back with cited sources and measured latency, and the guardrail blocks a request for personal data live.

Publishing with a working chat would require exposing the API over HTTPS, with its own domain declared in the visual's privileges. That's the project's next step — not a shortcut for the demo.
